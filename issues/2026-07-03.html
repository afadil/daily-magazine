06SecurityFor You
Regression · verify your kernel

Since Linux 6.9, LUKS suspend stopped wiping your keys.

The one guarantee that made a suspended laptop safe to carry — quietly broken.

The whole point of cryptsetup luksSuspend is to freeze I/O and flush the disk-encryption key out of RAM, so a suspended, encrypted laptop is worthless to a thief running a cold-boot attack. A newly surfaced report (Ingo Blechschmidt) finds that since Linux 6.9, that key wipe silently stopped happening — the key lingers in memory across suspend.

For a full-disk-encryption threat model built around “suspend before you cross a border,” this is the assumption collapsing underneath you. If you rely on LUKS suspend, treat suspended machines as if they hold live keys until you've confirmed behavior on your kernel — and watch the cryptsetup/kernel threads for a fix.

07Systems · Weird & Wonderful

The entire Rust compiler, rendered as 46 million lines of C.

A bootstrapping trick that lets Rust reach hardware LLVM never will.

crustc is rustc 1.98.0-nightly transpiled into roughly 46 million lines of C that compile with plain GCC and Make and produce a working compiler — one that can rebuild Rust's own standard library. The goal isn't novelty; it's reach. Obscure and legacy platforms often have a C compiler and nothing else, which has kept Rust permanently off them.

Underneath sits cilly, a Rust-to-C backend that doesn't assume a fixed C dialect. Instead it emits “witness programs” to probe what a given compiler actually supports (thread-local storage, void-pointer round-tripping) and tailors output accordingly. The demo even compiled Rust for x86 Plan 9 while running on ARM64 Linux, shuttling work over TCP. A pragmatic answer to the oldest question in language bootstrapping: what do you build the compiler with, when you have nothing?

08Search · InferenceFor You
14×

faster embeddings — by doing the opposite of what you'd expect.

Batching made it slower.

Manticore's old SentenceTransformers + Candle path was stuck at 5–11 docs/sec no matter the config, CPU idling. The ONNX Runtime rebuild hit 70–233 docs/sec — a ~14× average win — via a counterintuitive recipe: one shared session across threads, one document per call, no batching, intra-op spinning disabled (with_intra_op_spinning(false)), parallel tokenization at startup.

The insight worth stealing: on variable-length text, batching wasted compute padding short inputs to the longest in the batch, so single-doc calls won outright. And a spin-wait flag was burning cores for no work. Classic “measure, don't assume.”

✦Architecture in the Wild— the anchor read

How Cloudflare built saga rollbacks for Workflows.

Cloudflare Blog · Vaishnav Kavitha, Mia Malden & André Venceslau · June 25, 2026

Durable execution engines promise that a multi-step workflow survives crashes, retries each step, and remembers its progress. What they historically don't give you is the undo: when step 4 fails terminally, the money already debited in step 1 stays debited. Cloudflare Workflows now closes that gap with the saga pattern — every forward step can register a compensating action, and when the workflow dies, those compensations fire in reverse step-start order to unwind the world.

The engineering interest is in the seams. Compensation only triggers on terminal workflow failure, not on errors your own code catches — a deliberate line that keeps rollback predictable. Ordering uses persisted step-start order reversed (not completion order), so parallel workflows still unwind deterministically. And every rollback handler must be idempotent, leaning on idempotency keys from payment providers so a retried compensation never double-credits.

A step.do() already describes a durable unit of work that Workflows records, retries, and later shows in logs.

The API choice is the tell. Cloudflare rejected the fluent step.do().rollback() form because in Workers RPC a returned promise supports pipelining, which would make timing ambiguous for concurrent workflows; builder patterns felt too ceremonial. So rollback became plain metadata — { rollback: async ({ output }) => … } — attached to the step. Recovery after an engine restart runs in replay mode: workflow code re-runs without re-executing completed step bodies, rebuilding only the rollback handler stubs from persisted history.

Why it matters to a senior engineer: this is distributed-transaction theory (sagas, compensations, idempotency, replay) delivered as a two-line ergonomic API — and a clean case study in how API surface constrains, and is constrained by, the runtime beneath it. Today it's sequential-only; parallel rollback, waitForEvent, and Python Workflows are on the roadmap.
