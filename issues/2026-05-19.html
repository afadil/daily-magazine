02  Anthropic acquires Stainless.

Stainless — Alex Rattray's API-to-SDK compiler, founded 2022 — has generated every official Anthropic SDK since the start. It also generates the official client libraries for OpenAI, Google, Cloudflare, and Meta, across TypeScript, Python, Go, Java, Kotlin and more, and is now the dominant generator of MCP servers in the wild. The Information pegs the deal north of $300M; Anthropic is winding down all hosted Stainless products, including the public SDK generator, while letting existing customers keep what they've already generated.

Owning both the MCP standard and the primary toolchain that produces its servers is a structural lock on the agent surface. A model competitor now picks "build your own SDK generator" or "ship on Anthropic's pipes."

§ Architecture in the Wild · One deep read staff+ writing · postmortem · system design
№ A · Academic drop-cap · Cloudflare Engineering · May 14, 2026

The billing pipeline was slow. Nothing in the metrics said why.

Cloudflare's billing team migrated a ClickHouse partition key from (day) to (namespace, day) to enable per-namespace retention. The change worked. Then, over March 2025, the nightly aggregation job started getting slower — linearly with the cluster's total part count — even though each individual query read the same number of parts and the I/O, memory, and rows-scanned dashboards all looked clean. The hunt is the piece. trace_log and flame graphs eventually pointed at a single mutex inside MergeTreeData: hundreds of concurrent planners were taking exclusive locks to copy the entire parts vector — tens of thousands of entries — before filtering it down. Over 50% of query duration was spent waiting. The fix landed in three layers: swap exclusive locks for std::shared_lock, cache a shared copy so only the filtered slice was copied, then binary-search the sorted namespace key to prune parts without a linear scan. By March 2026 part count had grown from 30K to 160K per replica with query duration flat.

When the billing team first reported this problem we had 30,000 parts per replica. The part rate never stopped growing, and a year later we hit 160K parts per replica, but query durations have been stable thanks to the optimizations we made here.

The takeaway worth keeping: the dashboards Cloudflare's SRE practice is famous for — I/O, throughput, parts read — all said the system was healthy. The bottleneck was concurrency on a single in-memory mutex inside the query planner, invisible to the production-side telemetry, only visible by sampling the engine's own stack traces. If you operate any sharded analytical store at scale, the lesson reads cleanly: when query latency tracks the size of an internal data structure rather than the work the query does, look for a lock — and check whether the read path is taking exclusive ownership of state it never mutates.
